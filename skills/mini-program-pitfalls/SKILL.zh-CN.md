# Common Pitfalls for Early-Stage Mini-Program Development

小程序上线前踩过的坑，按"什么时候会撞上"排列，每条给**症状 → 根因 → 判据**。
末尾是一份可以逐项打勾的**上线前清单**。

> 这份文档是入口：它给全局地图和验收标准。
> 两个深度专题在 `../wechat-miniprogram-unfiled-backend/`（域名没备案怎么连后端）和
> `../wechat-pay-v3-refund-safety/`（支付退款怎么不重复出款）。

## 什么时候用

- 小程序要交审核 / 要上线，想知道还差什么
- 功能都"能跑"，但总有"这次好了下次又坏"的玄学
- 接手一个别人做的小程序后端，先做体检
- 出事故后复盘：想确认这是偶发还是结构性问题

## 坑的三层结构

大多数"玄学 bug"不是随机，而是三层的某一层被你忽略了：

| 层 | 你以为它在管什么 | 它真正在管什么 | 典型症状 |
|---|---|---|---|
| **运行时** | 我的代码 | 平台配额、冷启动、超时、进程存活 | 平时好的，忙时挂；夜里挂 |
| **数据** | 我写进去了 | 谁能写、并发时谁赢、写坏了怎么恢复 | 数据对不上、丢失、重复 |
| **通道** | 接口能通 | 域名备案、白名单、协议、缓存 | 开发者工具正常，真机不行 |

**排查顺序必须是 通道 → 运行时 → 数据**。
反过来做（先怀疑业务代码）会浪费最多时间，因为前两层坏了的表现常常长得像业务 bug。

## 一、通道层（最容易误判）

### 1. 开发者工具正常，真机全挂

**症状**：模拟器一切正常，扫码后首页空白 / 一直"离线" / 请求超时。
**根因**：开发者工具**不校验** request 合法域名、不拦 http 图片、还替你注入默认云环境。
真机三条全校验。
**判据**：真机上打开一次，能出首屏 + 能上传一张图 + 能进后台页。
**修法**：见 `../wechat-miniprogram-unfiled-backend/`。

### 2. 图片在真机上是空白，日志报 http 不支持

**症状**：`<wx-image>: 图片链接 http://... 不再支持 HTTP 协议`。
**根因**：`<Image>` 在真机只接受 https；开发者工具不拦。
**判据**：用户上传的图（头像/凭证/评价图）全部是 `cloud://` 或 https，没有一个 `http://IP`。
**修法**：用户图走云存储，不要存在自己的 http 端口上。

### 3. 后台能打开，但一直提示"密钥错误"

**症状**：输对密钥也进不去；本地同一套代码正常。
**根因**：登录接口本身被"仅允许带密钥访问"的门挡住了。登录请求天然没有凭据。
**判据**：非本机访问下，`POST /api/admin/login` 带正确密钥返回 200 + token（不是 403）。
**修法**：把登录路径放进放行清单；用非回环地址逐条验证。

### 4. 一个接口时好时坏

**症状**：同一功能，有时成功有时 403/超时，重试又能过。
**根因**：探活端点选错了。用"本来就放行"的路径（如健康检查）探活，探测通过 ≠ 真实接口能过。
**判据**：探活用的接口是**需要鉴权**的那种，探测失败时能正确降级。
**修法**：换探活端点；探测结果与真实请求走同一套准入逻辑。

### 5. 服务号推送报 40164

**症状**：模板消息/订阅消息发送失败，错误码 40164。
**根因**：微信要求调用方 IP 在白名单里，而云函数的出口 IP 是动态的、池子很大。
**判据**：有一台固定出口 IP 的中转（自己的服务器上一个 20 行的 PHP/Node 就够），云函数只把请求转发给它。
**修法**：固定 IP 中转；token 在中转侧缓存复用，别每次现取。

## 二、运行时层（配额与生命周期）

### 6. 云函数撞数量上限

**症状**：新建函数失败，或被告知已达上限。
**根因**：单环境云函数数量有**硬上限**（官方文档口径 50 个/环境，属系统参数）。
**判据**：函数数量有台账，距离上限留 30% 余量；新功能优先合并进已有函数（action 分派），而不是新建。
**修法**：按领域合并；把一次性脚本类函数（导入/回填/修复）用完就删。

### 7. 批量操作把函数打爆

**症状**：导出/回填/批量改价偶发失败，日志里是内存或超时。
**根因**：单次运行内存有上限（256MB 这一档），且函数超时默认很短。
**判据**：批量操作分页（每页 100~200 条），有进度记录，可断点续跑。
**修法**：分页 + 幂等 + 记录游标；不要把全表读进内存。

### 8. 欠费/配额打满导致全站 451

**症状**：某天开始所有接口、所有图片一起挂，代码没改过。
**根因**：平台侧欠费冻结或配额耗尽，与业务代码无关。
**判据**：有余额/配额告警（邮件或群机器人），有一条"平台侧故障"的对外话术。
**修法**：设告警；把关键静态资源做本地兜底。

### 9. 没有定时任务，订单永远停在中间态

**症状**：无人接单、超时未确认、超时未发货的单子越积越多，只能人工处理。
**根因**：代码里一个定时器都没有（云函数默认没有触发器，自建进程也需要显式 setInterval）。
**判据**：至少三条兜底在跑：超时未支付取消、超时未处理提醒/取消、超时未确认自动完成。
**修法**：云函数加定时触发器，或常驻进程加巡检；**所有兜底必须幂等**，并能在重启后按时间戳补算。

### 10. 服务挂过一次，之后数据不对

**症状**：重启后有几笔订单状态卡住，或重复结算。
**根因**：内存里的状态没落盘；或者落盘只写了一部分。
**判据**：写入是**原子**的（临时文件 + fsync + rename，或数据库事务）；重启后有补偿逻辑。
**修法**：原子落盘；关键状态机加"启动自检"，把卡住的任务重新入队。

## 三、数据层（一致性）

### 11. 客户端能直接改核心数据

**症状**：并发下库存/销量少算；或者用户能绕过界面改状态。
**根因**：业务写操作放在了客户端（小程序直接写库 / 直接调一个无校验的写接口）。
**判据**：库存扣减、订单状态流转、金额计算**只**发生在服务端；客户端只提交意图。
**修法**：把写操作上收到云函数或后端接口；客户端传"我想买 2 瓶"，不传"库存剩 8"。

### 12. 权限校验"只有超管能用"

**症状**：管理员/店员操作自己门店的数据，被拦"无权限"；超管一切正常。
**根因**：校验读的字段（如 storeId）在写入时没写（只写了展示用的 storeName）。
**判据**：**校验读哪个字段，写入就必须写哪个字段**；存量数据能从关联表回填。
**修法**：写入端补字段 + 校验端加兜底 + 存量回填一次，三件套一起做。

### 13. 加了新配置项，改了不生效

**症状**：后台保存成功，前端还是旧值；或者新枚举值一保存就变回默认。
**根因**：同一条数据被**多层白名单**过滤：前端传参 → 服务端保存 → 服务端返回 → 客户端解析。
**判据**：每加一个枚举/字段，四处白名单同步更新；用"改一个值 → 立刻读回"验证。
**修法**：把白名单收敛成一处定义，四处引用。

### 14. 批量操作永远处理 0 条

**症状**：批量删除/批量设置提示成功，实际一条没动。
**根因**：网关或转发层把数组/对象参数序列化成了字符串，`Array.isArray()` 直接判空。
**判据**：所有数组/对象入参都有 `typeof === 'string' ? JSON.parse : 原值` 的兜底。
**修法**：入口统一做参数归一化，别在每个 action 里各写一遍。

### 15. 备份有，但恢复不了

**症状**：误删后想回滚，发现备份是空的/格式变了/只有最近一份。
**根因**：备份只验证了"文件存在"，没验证"能恢复"。
**判据**：**真的恢复一次到临时环境**，比对行数与关键字段；备份保留窗口覆盖最坏情况（≥ 24 小时）。
**修法**：定期做恢复演练；备份与主库分离存放。

## 四、资金层（出事就是事故）

### 16. 把"接口返回成功"当成"钱到了"

**症状**：系统显示已退款，用户说没收到。
**根因**：退款申请返回 200 只代表**受理**，终态要等回调或查单。
**判据**：结算只发生在"收据四要素核对通过"那一刻。
**修法**：见 `../wechat-pay-v3-refund-safety/`。

### 17. 重试换了单号，退了两笔

**症状**：一笔订单出现两条退款记录。
**根因**：重试时生成了新的商户退款单号 —— 新单号 = 新的一笔退款。
**判据**：重试路径里 `out_refund_no` 来自任务记录，不是现场生成。
**修法**：先查后重试；只有"确定不存在"才用**原单号**重发。

### 18. 回调验签通过就入账

**症状**：金额/订单对不上，或出现陌生订单。
**根因**：验签只证明报文来自微信，不证明这笔钱属于这个订单。
**判据**：回调里必须核对订单号、金额、商户号、AppID 四项归属。
**修法**：验签 → 解密 → 核对归属 → 幂等入账，四步缺一不可。

### 19. 提现回滚导致余额被用两次

**症状**：用户提现后余额退回钱包，又提了一次。
**根因**：网络超时/5xx 时把提现判定成失败并回滚，但微信侧其实成功了。
**判据**：**结果不明 ≠ 失败**。不明就保持冻结、保持挂起，交给查单。
**修法**：先冻结后落定；只有明确失败（4xx）才释放；查单首次 ≥60 秒。

### 20. 提现/退款没有人工出口

**症状**：`ABNORMAL` / `CLOSED` 的单子永远卡住，没人知道要处理。
**根因**：只实现了自动流程，没有"转人工"状态和后台入口。
**判据**：后台有"需人工处理"列表，带单号、原因、金额、时间。
**修法**：异常态一律落 `manual_review`，并在后台可见。

## 五、发布与运维

### 21. 改了配置，nginx 说成功但没生效

**症状**：面板保存成功、`nginx -t` 通过、reload 返回 0，行为一点没变。
**根因**：reload 时 bind 失败（常见是某个配置文件 `listen` 撞了已被占用的端口），master 保持旧配置继续跑，只写 error_log。
**判据**：改完看 `error_log` 尾部 + worker 启动时间有没有变。
**修法**：找到坏 conf 隔离掉再 reload；`exit 0` 不等于生效。

### 22. 反向代理开了缓存，用户看到别人的数据

**症状**：不同账号看到同一份订单；健康检查里的 uptime 一直是同一个数。
**根因**：反代或 CDN 缓存了接口响应。
**判据**：连续刷新健康检查，`uptime` 每次都在增长；两个账号数据互不相同。
**修法**：接口路径关缓存（`proxy_no_cache` + `Cache-Control: no-store`）。

### 23. 不知道线上跑的是不是自己测的版本

**症状**：修复"上线了"但用户说没变。
**根因**：只对比版本号，而版本号忘了改。
**判据**：找一个**只有新代码才有的行为**（新路由返回 401 而不是 404、某字段从写死变成实算）。
**修法**：部署后跑一条"新功能探针"，而不是看版本字符串。

### 24. 审核被拒，理由是"功能无法体验"

**症状**：审核员说登录不了 / 看不到核心功能。
**根因**：核心功能要真实手机号、要审核通过、要余额，审核员没有。
**判据**：准备一个体验账号（账号+密码，非短信），带足体验数据，写进审核备注。
**修法**：体验账号开关做成配置项，审核结束就关掉；配一份操作路径说明。

### 25. 上线后没有观测手段

**症状**：用户报错，你只能猜。
**根因**：没有健康检查、没有错误日志聚合、没有关键业务计数。
**判据**：`/api/health` 返回版本、运行时长、关键依赖状态；错误日志可按时间检索。
**修法**：健康检查 + 结构化日志 + 一条"每分钟核心指标"的巡检。

## 上线前清单（逐项打勾）

> 完整可打印版：`references/launch-checklist.md`

### A. 资质与平台配置

- [ ] 域名已备案，且备案主体与小程序主体一致
- [ ] 后台「request 合法域名」已添加，含 API 域名与地图等第三方域名
- [ ] 小程序类目与实际功能匹配（涉支付/医疗/教育等有额外资质要求）
- [ ] 用户隐私保护指引已填写，且与实际收集的字段一致
- [ ] 订阅消息模板已申请并通过，模板 ID 写进配置
- [ ] 微信支付商户号已开通对应产品（JSAPI / 商家转账等）
- [ ] 支付回调地址可达（公网 HTTPS，且不被反代缓存）
- [ ] 审核用体验账号已准备，且不依赖短信验证码

### B. 后端与数据

- [ ] 云函数/接口数量距离平台上限还有余量（建议 ≥30%）
- [ ] 批量操作已分页，且有断点续跑能力
- [ ] 至少三条超时兜底在跑，且幂等、重启后能补算
- [ ] 写操作只在服务端；客户端不直接改状态与库存
- [ ] 金额全程用整数分，不经过浮点
- [ ] 关键写操作是原子的，落盘失败会停止业务而不是继续
- [ ] 备份可用，且**真的恢复过一次**
- [ ] 数据库/存储的容量与配额有余量
- [ ] 关键集合/表有索引，列表接口不会全表扫

### C. 资金

- [ ] 支付回调：验签 → 解密 → 核对归属 → 幂等入账
- [ ] 退款：申请、幂等、结果确认、状态持久化四步齐全
- [ ] 退款重试使用原单号；先查后重试
- [ ] 退款在支付成功 365 天窗口内校验
- [ ] 提现：先冻结后落定；结果不明不回滚
- [ ] 异常态（ABNORMAL/CLOSED）有后台人工入口
- [ ] 每日对账：本地账本 vs 平台账单，差异有清单
- [ ] 密钥只在服务端，不硬编码、不进日志、不进接口响应

### D. 前端与真机

- [ ] 真机跑通：首屏、登录、下单、支付、上传图、后台页
- [ ] 用户图片全部走 https 或 `cloud://`，没有 http 图片
- [ ] 云开发的 `cloud.init` 是真调用（不是只有标志位）
- [ ] 所有状态码分支（401/403/业务错误）都有对应 UI
- [ ] 弱网/超时有兜底提示，不是一直转圈
- [ ] 首屏不依赖"必须登录才能看"的接口

### E. 发布与回退

- [ ] 版本号在"唯一来源"里维护，页面「关于」读到的是它
- [ ] 有灰度或体验版验证路径
- [ ] 有明确回退方案（上一版代码 + 数据兼容）
- [ ] 部署后能用"新功能探针"确认线上是新代码
- [ ] 健康检查暴露版本、依赖状态、关键计数
- [ ] 余额/配额/证书到期有告警
- [ ] 知道出事时第一句话怎么说（对外沟通话术）

### F. 上线后 24 小时

- [ ] 核心链路成功率（登录/下单/支付/退款）有数字
- [ ] 错误日志无新增的重复异常
- [ ] 定时任务真的在跑（看日志，不是看配置）
- [ ] 备份正常生成
- [ ] 没有"卡在中间态"的订单堆积

---

## 怎么用这份清单

1. **别一次全做**。先跑 A/D 两组（不做就上不了线），再跑 C（出事最贵），最后 B/E。
2. **每项都要有证据**。"配了"不算，"实测返回 200" 才算。
3. **把清单变成脚本**。能自动化的（健康检查、域名可达、函数数量、备份存在性）就别靠人记。
4. **每次上线只加一条新检查**。清单太长就没人看，保持 40 项以内。
